# 手机端沙盒交接：离家检查

本轮是 homie「未来家庭」Android 入口的布局与挂载准备。没有引入正式 3D 引擎、GLB、Home Assistant、后端连接或设备控制。设备名称、房间、品牌型号和备注来自现有本地家具目录；用电及状态数值来自明确标为“演示数据”的独立静态样例。

## 已有页面与模块

- `src/features/sandbox.ts`：`renderSandbox()` 生成手机页面结构，`mountSandbox(container, context)` 读取家具目录并挂载事件，仍返回卸载函数。
- `src/features/sandbox.css`：沙盒专属布局。上方是场景区，下方是设备、只读详情或离家任务面板；页面给底部导航和安全区留白。
- `src/features/sandbox-scene.ts`：`#sandbox-scene-mount` 的本地呈现控制器，提供占位、加载、失败三种状态。当前默认显示静态 SVG 示意图。
- `src/features/sandbox-demo.ts`：只用于演示的固定读数；普通设备用电、家庭储能充电、太阳能发电分开显示，旧的非用电家具没有虚构读数。
- `src/features/sandbox-copy.ts`：沙盒中英文文案，跟随现有语言设置；用户填写的文字保持原文。

沙盒没有添加、编辑或删除家具的入口。家具继续在“添加”页登记。点设备卡片打开只读详情；全屋复位、模型定位、计划执行和控制等未接入操作保持不可用。任务页中的玄关门检查只是人工检查入口的占位，不会因为定位或点击模型而自动完成检查。

演示数据不是设备检测结果，不会写入 `homing.app.v1`，也不会产生真正的设备状态或控制指令。页面中的数据标记必须在未来演示模式下继续保留。

## 最终资产的接入位置

下列是预留的文件位置；收到实际资产后再添加文件并确定模块接口。当前页面不会请求不存在的资产。

| 交付内容 | 预留位置 | 用途 |
| --- | --- | --- |
| 固定小公寓 GLB | `public/sandbox/apartment/scene.glb` | 未来加载到 `#sandbox-scene-mount`；如模型引用外部贴图，保持同目录内相对关系 |
| 实际对象映射表 | `public/sandbox/apartment/object-map.json` | 保存资产交付方提供的 `room_id` / `object_id` 与模型对象映射；具体字段待实际文件确定 |
| 3D 渲染适配 | `src/features/sandbox-runtime/model.ts` | 接管场景挂载、视角复位、定位与高亮，提供可卸载的渲染生命周期 |
| 状态运行时适配 | `src/features/sandbox-runtime/state.ts` | 接入实际状态模块或其样例，管理订阅及清理；具体接口等模块交付后确定 |
| 目录与对象关联 | `src/features/sandbox-runtime/bindings.ts` | 显式关联本地家具、模型对象和设备状态，不混用不同来源的 ID |

以上运行时目录本轮没有创建实现，不预先定义后端协议或伪造对象映射。`sandbox-scene.ts` 的 `show()` 仅控制当前页面的占位、加载和失败展示，不是最终状态运行时接口。

## 数据归属与关联

家具目录、模型映射和设备状态是三个独立的数据来源：

1. 家具继续通过 `context.getFurniture()` 获取，复用主 App 的唯一 store。返回值是副本，沙盒不创建第二个 store。
2. 家具保留本地 `id`、房间名称、品牌型号等现有字段。`model` 是品牌/型号文字，不能作为 GLB 路径。
3. 模型热点、详情与任务使用资产交付方提供的 `room_id` / `object_id` 关联。不能从中文房间名、翻译后的英文名或家具名称推导稳定 ID。
4. 真实状态及其时间、有效性来自后续状态运行时。本地家具 ID 不应被当成设备状态 ID。
5. 使用独立关联表完成显式绑定。若未来需要持久化绑定，届时单独确定存储及迁移方式；本轮不改变现有存储结构。

新增家具选项为 15 个智能设备类别。`FURNITURE_TYPES` 用于新增入口；`ALL_FURNITURE_TYPES` 还保留旧分类，供旧存档读取、展示及编辑。删除新增入口不等于删除用户的旧家具记录。默认房间改为八个，但旧房间和自定义文字仍可读取和保存。

## 生命周期和返回操作

主页面每次切换导航或语言时先调用上次 `mountSandbox()` 返回的清理函数，再渲染和挂载。该边界保持不变。

正式模块接入时，在 `mountSandbox()` 内取得场景容器，先显示加载状态，再启动模型加载和状态订阅；成功后挂载真实场景，失败时显示失败状态并保留家具面板。卸载时应：

- 标记本次挂载已失效，取消未结束的加载；晚到的结果不得写入下一次页面。
- 解绑点击、返回、窗口事件、观察器和订阅。
- 停止动画帧及计时器，释放渲染器、材质、纹理及几何体。
- 释放当前选中设备、计划高亮等页面状态，避免再次进入时重复响应。

当前 `mountSandboxScene()` 的 `dispose()` 会使后续 `show()` 不再改写容器。真实 GLB 加载器也需要遵守这一失效保护。

主入口收到 Android 的 `homing:back` 后，会先向当前沙盒容器派发可取消的 `homie:sandbox-back`。详情面板消费该事件并回到设备列表；列表不消费，主入口再回到添加页。沙盒使用独立的 `data-sandbox-action`，不复用主页面会触发编辑、删除的 `data-action`。

## Vite 与 Android 资源路径

Vite 的 `base` 保持 `./`。`public/` 中的资源会原样复制到 `dist/`；后续加载上述 GLB 时可以从应用基础地址解析：

```ts
const modelUrl = new URL(
  `${import.meta.env.BASE_URL}sandbox/apartment/scene.glb`,
  document.baseURI,
).href;
```

对象映射和贴图使用相同的基础路径。不要写电脑绝对路径、`file:///`、`/public/...`，也不要假定网站总部署在域名根目录。若后续改用 `src/` 内导入资产，应由 Vite 的静态导入或 `new URL(..., import.meta.url)` 处理输出文件名。

Android 构建前运行 `npm run android:sync`，把最新 `dist/` 同步进 Capacitor 原生工程，再构建 APK。`scripts/build-android.ps1` 已包含这一步。不能只构建前端而跳过同步。最终 GLB、贴图和映射应随安装包打包，除非后续明确改为远程资源策略。

## 下一轮真实演示的状态边界

目标流程：全屋复位 → 点提醒定位玄关 → 点客厅灯查看详情 → 高亮关灯计划 → 收到有效设备读数后，画面里的灯熄灭。

- 定位只改变观察位置或选中对象，不意味着任务完成。
- 普通玄关门只提供人工检查，不生成自动开关门控制。
- 计划高亮展示将要执行的内容，不提前改变设备实际画面。
- 指令受理只更新受理反馈，不能当作设备执行成功。
- 灯的真实亮灭由状态运行时确认有效的设备读数驱动；错误、缺失、过期和未知读数不应被转换成“关闭”。具体有效性规则等实际模块交付后确定。

## 验证范围

重点验证 360px / 390px 布局、中英文、家具详情与返回、反复挂载卸载、旧存档保留，以及演示数据不写入存储。WebView 或真机表现必须有实际运行证据才能记录；APK 构建成功、桌面浏览器手机尺寸截图均不能代替真机测试。
