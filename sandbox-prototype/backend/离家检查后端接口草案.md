# 离家检查后端接口草案

版本 0.2 · 2026-11-14 · 以共享约定 v0.5 为准

首条联调路径为 `baseline_apartment`。本稿所列 HTTP 路径、状态码、封装和新增字段均为建议，待三方确认。实际请求与响应样例见 [离家检查联调样例.json](./离家检查联调样例.json)，交付依赖见 [离家检查联调准备清单.md](./离家检查联调准备清单.md)。

## 1. 状态分工

| 独立事实 | 记录与更新来源 |
| --- | --- |
| 本人是否出门 | `user_away: true / false / null`，由发起人单独声明。开始基线时为 `false`。 |
| 家中是否有人或宠物 | `occupancy: occupied / empty / unknown`，搭配 `retain_room_ids`。可补充 `context.room_occupancy`。生成计划时由用户核对，出门声明与门窗读数各自更新。 |
| 玄关普通门人工核实 | `manual_records` 按任务和 `entry_door` 记录 `pending / confirmed_closed / deferred`。只有现场确认关闭后记录 `confirmed_at`，在该任务投影 `state=closed, source=manual, updated_at=confirmed_at`，且始终 `availability=not_applicable`。待核实或稍后核实时为 `unknown`，来源和证据时间均为空。上锁另行人工核实。 |
| 阳台门磁 | `balcony_door` 使用 `source=sensor` 的有效 `open / closed` 读数。离线或过期时当前为 `unknown`，`source`、`updated_at` 为空。只有可信历史读数、时间和来源齐全才展示最后读数。历史字段见下文。 |

全量快照带 `schema_version`、`template_id`、`demo_mode`、按 `object_id` 键控的 `objects`，可附家庭状态、`context`、`capabilities`、`plan`、`manual_records`、`execution` 和 `energy`。各响应带 `template_id` 与 `demo_mode`。状态读取和演示复位给全量快照；其它响应按下表更新各自的数据。前端用 `replaceSnapshot` 装载全量，用 `patchObjects` 按对象深合并增量。遗漏键保留，显式 `null` 清空；从离线恢复时显式清空已无须展示的历史字段。拒绝错误模板、未知对象、房间不匹配和非有限数值。旧资产缺模板时按小公寓处理，前端按 `(template_id, shared_id)` 隔离空间索引。

计划目标只驱动虚线覆盖层，执行状态只驱动任务面板。3D 与设备详情使用对象证据，收到指令受理、等待、失败或任务完成状态时，保持当前对象读数直到有效新证据到达。读数到期时按未知显示。灯关闭后仍可为 `power_state=powered`。未知与断电分别呈现，温度、定时等沿用共享遥测语义。全屋复位只处理镜头及选中项，演示复位由状态数据驱动。

### 响应更新范围

| 响应类型 | 入口及识别 | 应用范围 |
| --- | --- | --- |
| 全量快照 | `GET /demo/leave-check/state`、`POST /demo/leave-check/reset` 成功 | 将快照交给 `replaceSnapshot`。产品页面按快照携带的范围初始化设备、对应任务和能源数据。读取指定任务时用请求的 `task_id` 或快照的 `plan.task_id` 关联。普通状态读取只水合明确关联的数据，未绑定任务的快照中 `plan: null`、`execution: []` 等基线值不清空当前任务。 |
| 对象增量 | 重新读取对象、人工核实、执行提交或回读查询等响应中含 `objects` | 把 `{template_id, objects}` 投影交给 `patchObjects`，并用同批有效对象证据更新设备详情。当前 provider 对整个入参做深合并，调用方须提取对象投影。无 `objects` 时跳过对象更新。 |
| 离家任务更新 | 生成或更新计划、本人出门、人工记录、执行提交、执行查询、带检查或执行结果的刷新，以及返回新计划的 `409` | 按会话和 `task_id` 更新对应任务。任务标识可从响应、`plan.task_id` 或请求路径取得。按 `task_id` 和 `execution_id` 找执行记录，再按 `item_id` 更新逐项结果。确认成功后将选中集与该执行绑定；查询与刷新保留原选中集及其它执行。 |
| 能源更新 | 能源采样、预览、预授权校验 | 采样只更新 `energy` 与提醒状态。预览按响应 `task_id` 或 `plan.task_id` 更新独立能源预览，关联离家任务仅提供上下文；预授权结果按该能源预览任务关联。三类响应均省略设备 `objects` 和 `execution`。 |

混合响应逐段应用。例如门磁刷新把 `objects` 给设备状态层，把 `checks` 给匹配任务行；执行回读把 `execution` 给任务面板，把同期 `objects` 给设备状态层。字段缺席时保留相应数据。只有当前模拟会话的显式演示复位成功后，才按基线清空该会话的任务、选中集、人工记录、执行和能源提醒。复位请求失败时保留这些数据，复位成功后忽略旧代次响应。

### 阳台离线历史

- 后端草案沿用 `last_known_state` 和 `last_known_at`，建议以 `last_known_source` 携带已核验的历史来源。离线/过期时当前 `state=unknown`，本稿的当前 `source`、`updated_at` 均为 `null`。门磁历史须有 `open / closed`、可信的门磁来源和带时区的证据时间。缺失时省略历史行。
- 当前 `state-provider.js` 的 `invalidate` 可能把离线或过期载荷中带来源、时间的残留值写成 `last_known_values.state`，设置 `last_known_at` 并清空当前 `updated_at`。该路径保留对象的原 `source`，未单独写入 `last_known_source`；当前 `state-bridge.js` 转发 store 归一化快照。原始 `offline` fixture 因此可以生成历史形状，历史证据仍须单独核验。
- 建议后端在业务对象出口归一化实况并保留可信历史，前端在桥接输入适配或展示投影边界统一取 `last_known_state` 或 `last_known_values.state`。嵌套形状只有在来源和时间能同批核验时才映射，优先采信显式历史来源或同对象此前已在线验收的读数记录。普通当前 `source` 或离线残留值本身不足以证明历史。两个形状冲突时使用可信证据，否则省略历史。待建模侧确认最终桥接字段形状、历史来源传递及归一化分工。

## 2. 离家任务动作

下表路径均为待确认。静态样例中的 HTTP 方法、路径、状态码、证据时钟及结果用于对照页面走查。

| 业务动作 | 建议入口 | 请求 | 响应、状态变化与错误反馈 |
| --- | --- | --- | --- |
| 读取当前状态 | `GET /demo/leave-check/state?template_id=...` | 模板，建议可选 `task_id` 读取指定任务视图 | `200` 全量快照，基线含灯亮、空调运行、玄关无证据、阳台已合上；任务不存在返回 `404`。历史证据单独返回。 |
| 重新读取对象 | `POST /demo/leave-check/state/refresh` | `template_id`、可选 `task_id`、`object_ids`；核查执行时带 `execution_id` | `200` 返回对象增量，可附属于对应 `task_id` 的门磁 `checks`，或属于对应 `task_id` 与 `execution_id` 的执行复核结果。门磁失联返回该对象的离线态，可继续重新读取；整体状态源不可用返回 `503 STATE_UNAVAILABLE`。 |
| 生成或更新计划 | `POST /demo/leave-check/plans` | `template_id`、`intent_text`、经用户核对的 `occupancy`、`retain_room_ids`，可选 `room_occupancy`；更新带 `task_id` | 新建 `201`，更新 `200`，返回 `task_id`、家庭条件、人工清单及 `plan`。更新留家条件时保留本人出门记录。未知占用可返回保守预览和补问；互相矛盾的约束返回 `422 CONSTRAINT_CONFLICT`。 |
| 记录人工核实 | `PUT /demo/leave-check/tasks/{task_id}/manual-records/{object_id}` | `result`，基线可提交 `confirmed_closed` 或 `deferred` | `200` 返回更新后的人工记录和玄关对象增量，首次确认时间由后端记录，重复同结果复用原证据。玄关继续待办时可再次现场核实。对门磁提交人工关闭或使用非法结果返回 `422`。 |
| 确认本人已出门 | `PUT /demo/leave-check/tasks/{task_id}/user-away` | `user_away: true` | `200` 返回本人声明与原留家约束。页面可以连续引导现场核实和出门声明，两步分别提交和反馈。 |
| 执行选中项 | `POST /demo/leave-check/tasks/{task_id}/executions` | `plan_version`、`confirmation_id`、`selected_item_ids` | `202` 返回 `task_id`、`execution_id`、`plan_version`、`selected_item_ids` 和逐项 `execution`，可附对象增量。过期或相关条件变化返回 `409 RECONFIRM_REQUIRED`，附最新计划、`affected_items` 和可用对象增量，本次提交发出零条设备指令。无有效勾选、非 action 项、非法 ID 返回 `422 INVALID_SELECTION`。 |
| 查询逐项回读 | `GET /demo/leave-check/tasks/{task_id}/executions/{execution_id}` | 任务与执行 ID | `200` 返回关联任务与执行的逐项状态，可附对象增量；部分失败也走 `200`。未知执行 ID 返回 `404`。 |
| 演示复位 | `POST /demo/leave-check/reset` | `template_id` | `200` 恢复当前模拟会话基线快照，清空计划、人工核实、执行、能源提醒和去重记录。旧任务和执行 ID 失效。模拟回读按会话代次隔离，避免复位后迟到结果覆盖基线。 |

会话由服务端上下文隔离，联调时确认具体标识。路由建议采用读写分离和按需轮询。请求格式错误用 `400 INVALID_REQUEST`，业务校验失败用 `422`，资源不存在用 `404`。错误体使用 `error.code` 和可展示的 `error.message`；逐项错误同形。轮询间隔、读数有效期、等待回读期限和并发限额待与适配层确认。

### 计划生成、确认与重复提交

- 每个计划项返回 `item_id`、`object_id`、`group`、`current_state`、`target_state`、`action`、`reason`、`selected` 和 `evidence`。基线把客厅灯归 `action`（默认选中），卧室空调归 `keep`，玄关归 `manual`，阳台归 `check`。阳台离线时允许重新读取。灯已关时落入无需动作的 `check`。独立关灯可在玄关 `pending / deferred`、本人尚未声明出门时确认执行，前提是客厅无人且设备能力与读数满足条件。
- 结合占用、保留房间、其它保留规则和有效设备读数生成候选。留家状态未知时补问或保留可能影响住户与宠物的设备。全员离家、空调在线开启且无其他保留条件时，`bedroom_ac` 进入 `turn_off` 候选，默认不勾选。用户提交的 ID 列表表示对该版本候选的明确勾选，空调需主动加入。只发后端允许的动作。
- 执行前比较最新版 `plan_version`、留家/保留条件、允许动作、对象状态及证据有效性。状态变化、过期、失去能力或保留条件变化影响提交时，重算并递增版本，返回受影响条目和原因。读数更新时间变化且业务条件仍等价时可继续原确认。页面复核受影响项，针对新版本重新提交，只为仍可执行且已选中的项下发。灯已由外部关闭时按最新读数显示关闭，并归入无需动作。
- 采用按会话与 `task_id` 限定的 `confirmation_id`。后台原子登记版本和选中集，再安排下发。相同 ID、版本及选中集的重复请求（顺序不同视为同一集合）复用原执行 ID 与已知结果；并发提交共用同一记录。相同 ID 配不同内容返回 `409 CONFIRMATION_CONFLICT`。对同任务同项正在执行的重复新 ID 返回 `409 ACTION_IN_PROGRESS`，并引导查询原执行。刷新后确需重试时，使用当前版本、新确认 ID 和实际需要重试的条目。复核与下发之间若相关条件再次变化，停止尚未发出的受影响项并逐项反馈。

### 阳台检查只显示一条

- 当前任务的 `plan.items` 若有 `balcony_door` 的 `group=check`，用该行的 `item_id` 渲染。刷新响应的 `checks` 按 `task_id + item_id` 匹配，校验 `object_id` 与当前计划版本，更新该行的检查结果及证据。读数取该对象最新的有效状态，离线按未知处理，同时保留任务行身份和重新读取入口。
- 当前计划没有这条 `check` 时，以 `balcony_door` 对象读数显示一张只读检查卡。相同对象只呈现一条阳台检查结果。执行按钮的数量仅统计当前勾选的 `group=action`，阳台检查永远不计入。
- 建模依赖为 `balcony_door` 到实际节点、热点和相机目标的可用映射。任务行、只读卡的选择和数量由前后端确认。

### 指令发出与回读

| 执行状态 | 反馈与证据 |
| --- | --- |
| `pending` / `running` | 排队 / 下发中，任务面板显示处理进度。 |
| `awaiting_readback` | 已发送并被适配层受理，建议返回 `command_sent_at` 和 `command_accepted=true`。文案「指令已发出 · 等待设备回读」。 |
| `confirmed` | 收到不早于本次下发、来源有效且达到目标的回读。记录 `readback_state`、`readback_at`，对象增量可随响应到达，也可独立到达。后续实况仍按最新有效对象读数更新。 |
| `failed` | 明确拒绝、适配器明确报错或执行前条件不再满足。逐项给出错误，有读数则单列。 |
| `unknown` | 超时或无法判定指令是否生效。文案「结果待核实 · 请先刷新状态」。 |

执行项含 `item_id`、`object_id`、`status`。没有回读时 `readback_state` 和 `readback_at` 为 `null`。超时先刷新关联执行及对象：有效目标读数可确认原执行；新鲜读数仍未达目标时，保留待核实并按能力和当前条件返回 `retry_eligible_item_ids`；仍无有效证据时继续待核实。重试只面向允许重试的未达成项，经用户重新确认；部分失败可单独复核失败项，已确认项保留在原执行记录。

设备与执行各按自己的证据和时间更新。对象增量按对象及其 `source`、`updated_at`、`availability` 核验并处理读数顺序；执行按 `task_id + execution_id + item_id` 使用执行状态及 `readback_at` 等回读证据。历史回读时间记录本次执行确认，设备详情时间记录当前对象证据。

- **样例 A：对象读数先到。** 独立刷新先给有效 `off`，设备详情和 3D 显示关灯，执行仍等待回读。随后查询拿到 `confirmed` 才完成任务行。
- **样例 B：执行确认先到。** 任务行先显示已确认。缺少同步到当前设备缓存的对应读数时提示「最新设备读数待同步」。已有读数有效时沿用其状态，过期时显示未知。收到对应的有效 `off` 后更新实况并去掉提示。若已收到证据时间更新的独立读数，则显示该读数并保留原执行的确认时间。

## 3. 能源备用分支

| 业务动作 | 建议入口 | 请求及校验 | 响应 |
| --- | --- | --- | --- |
| 评估能源采样 | `POST /demo/energy/samples` | `template_id`、家庭时区、计量口径、月度上限、当月天数及 `measurements`；联调阶段注入模拟读数。旧采样和离线/过期数据不触发新提醒。 | `200` 返回 `energy` 和 `new_notice`。无效口径、单位或数值返回 `422`。 |
| 查看省电计划 | `POST /demo/energy/plans` | `template_id`、关联离家 `task_id`、`alert_ids`、`objective` | `201` 返回独立能源预览 `task_id` 及 `plan`。合并同对象同动作的候选，保留各触发原因。提醒不存在或已失效时提示刷新。 |
| 校验预授权 | `POST /demo/energy/authorization/check` | `template_id`、预览 `task_id`、`plan_version`、`alert_ids`、`selected_item_ids`、`authorization_id`（无则 `null`） | `200` 返回预览 `task_id`、`allowed`、`mode`、`reason_code` 和逐项可用性信息。缺少或不满足授权示例为 `preview_only`，无指令下发。该校验入口本身为只读判定。 |

- 日参考线按月度上限 ÷ 当月天数计算。演示按 `Asia/Shanghai`、`household_consumption`，300 ÷ 30 = 10 kWh。从 10 采到 12 kWh 时显示「比今日参考线多用 2 kWh」，月累计 128 kWh。仅有购电数据时用 `grid_import` 并显示「购电预算」。按家庭、当地日期、口径和告警类型去重，同日更新沿用 `alert_id`；月超额独立按自然月归并。预览对象与提示来自后端。
- `energy.measurements` 按指标返回 `value`、`unit`、`source`、`updated_at`、`availability`、`data_kind`。估计另给 `assumptions` 与 `basis_kind`。`energy.alerts` 包含 `alert_id`、`kind`、`message`、`object_ids`。电池为全屋只读对象。低备电量仅建议已验证在备电回路上且满足留家约束的非必要负载，和日超额命中客厅灯时可合并为一个动作。冰箱、运行中洗衣机等不进入普通断电建议。
- 演示默认提醒或预览，后续可用显式确认执行模拟省电任务。真实自动省电须检查授权身份及家庭范围、有效期及暂停/撤销状态、触发范围、逐台允许的动作、留家约束、设备能力、读数新鲜度与重复执行限制。真实指令要求 `verification_scope=physical` 且有逐台验证和授权，实际下发前再次复核。

- **有阳台检查行时刷新门磁** · `balcony_refresh_with_check`。基线计划已有 `item_balcony_door` → `POST /demo/leave-check/state/refresh` 同时返回 `objects` 和 `checks`。原行显示开启，一条阳台结果、一个选中动作。
- **无阳台检查行时显示只读检查** · `balcony_refresh_without_check`。`POST /demo/leave-check/plans` 返回无阳台检查行的版本 → 刷新仅返回 `objects`。只读卡从已合上更新为开启，一条阳台结果、一个选中动作。
- **样例 A：对象读数先到** · `object_readback_first`。待回读 → 对象刷新返回 `off` → 查询执行返回 `confirmed`。灯先灭，任务后完成。
- **样例 B：执行确认先到** · `execution_confirmation_first`。待回读 → 查询执行返回 `confirmed` → 对象刷新先返回过期未知、再返回有效 `off`。任务先确认并提示待同步，实况由亮、未知更新为灭。
