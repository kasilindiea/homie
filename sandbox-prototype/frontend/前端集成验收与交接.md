## 4. 待接后端的数据入口

正式联网前，前后端分别完成独立验收后再联调。当前 `LocalGateway` 是内存模拟器，未来以 transport 适配器替换，界面继续使用 `ProductStore.applyResponse`。建议路由仍以 backend 草案为待确认依据，本轮没有把它们实现为可调用服务。

| 业务入口 | 本地对应 | 正式适配要提供 |
| --- | --- | --- |
| 状态 / 演示复位 | catalog.baseline_snapshot、`gateway.reset()` | 全量快照、模拟会话标识、显式复位成功回执与代次隔离；不能用普通查询清空任务 |
| 生成计划 | `gateway.createPlan({intent, everyone})` | `task_id`、`plan_version`、留家条件、分组、默认选择、证据与允许动作；全员离家空调默认未选 |

| 执行确认 | `gateway.execute(...)` | 版本、确认 ID、选中集、执行 ID、逐项结果；确认前变化返回受影响项，明确重复确认语义 |

## 5. 给建模 / 状态负责人确认的既有差异

**M-01：失效载荷的历史形状需要独立证据来源，非本轮集成阻断。**

- 使用版本：state-driven-v0.3 `state-provider.js`，SHA256 `299eeb6f38ff171459751accb5b5758e23fa7e2cf4242892f7558b3ddecd0b04`；后端 v0.2 草案也记录了此差异。
- 复现：给原始 `DeviceStateStore` 输入 `balcony_door`，保留 `state=closed/source=sensor/updated_at`，同时设置 `availability=offline`；`invalidate` 会把残留值转成 `last_known_values.state/last_known_at`，保留原 source，但不单独提供 `last_known_source`。
- 预期：当前状态为 unknown；只有能独立核验的历史来源、状态、时间才可显示历史。离线残留字段自身不能证明历史可信。
- 前端处理：在进入交付状态库前将失效当前字段清空；只接受来源与时间齐全的历史证据。对后端明确提供的 `last_known_state/last_known_source/last_known_at` 显示历史；不从 provider 自动生成的形状推导可信历史。已用两个单元用例检查有历史 / 无历史。
- 待建模与后端确认：最终历史来源字段、嵌套历史形状的来源传递，以及归一化由业务出口还是桥接层承担。当前保守处理只在 frontend，不修改共享约定、fixture 或交付运行时。

`state-bridge.js` 依赖独立查看器的调试 DOM，本轮按建模交接建议直接复用 `DeviceStateStore`，自建产品布局绑定；这属于前端接入选择，不作为模型缺陷。
