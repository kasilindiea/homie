日期：2026-11-14。起点：`baseline_apartment`，1440 × 900 桌面画板。

本稿交付产品页面规格、低保真线框、3D 区域预留与交接清单。页面开发、模型嵌入、状态桥接、依赖安装、服务启动及后端接线，均等待后续指令。本稿中的页面行为与验收结果是设计预期，不代表已经实现或通过联调。

## 2. 对 DS 原稿的语义修正

以下规则用于新页面规格，不回写 DS 原稿或共享约定。

| 冲突位置 | 本稿采用的页面规则 | 观察点 |
| --- | --- | --- |
| DS §2.1「我已确认关闭 · 现在出发」合并了两个动作 | 玄关面板按钮改为「我已确认关闭」与「稍后核实」。本人状态在顶栏独立显示，通过「我已出门」单独声明。人工记录只属于本任务、本对象。 | 确认玄关关闭后，`user_away=false` 仍显示「本人：未出门」；点击「我已出门」不自动核实玄关，也不清除猫留卧室的约束。 |
| DS C4/C5、超时刷新描述把设备实况与执行结果耦合 | 设备详情和 3D 实况由有效对象读数驱动；执行行由 `execution` 每项 `status` 表达。页面不从 `target_state`、指令受理或 `status=confirmed` 合成设备读数，也不仅因对象读到 `off` 就改写执行结果。 | 有效 `off` 先到，灯先灭，执行行仍可等待结果；执行确认先到，任务显示收到确认，实况仍按已有读数显示并提示「最新设备读数待同步」。 |
| DS §五建议把离线快照残留 `state` 自行转为历史读数 | `offline/stale` 按归一化状态显示：当前枚举为 `unknown`，失效数值为 `null`。只有明确的 `last_known_state/last_known_at`，或可核验的此前有效读数及其证据时间，才显示历史行。缺失历史证据就不显示最后状态、最后时间。 | 现有 `offline` 中残留的 `closed/on` 不作为当前或历史证据；显示「状态未知 · 设备离线」。未知门的静态/保留姿态不表示已合上。 |
| DS A3 将空调候选误写为「关灯」 | 全员离家、`occupancy=empty`、卧室不再保留且无其他保留规则时，显示「关空调候选」，默认不勾选；仍须允许动作及执行前复核。 | 不由 `user_away=true` 单独推导全员离家，不自动关闭空调。 |

本人状态的三种文案分别为：`false` →「本人：未出门」，`true` →「本人：已出门」，`null` →「本人：未声明」。留家约束另列「猫留卧室 · 保留卧室空调」；`occupancy=unknown` 时先补问，或保留可能影响住户、宠物的设备。

设备实况与任务结果并列示例：

| 收到的信息 | 设备详情 / 3D | 任务结果行 |
| --- | --- | --- |
| 计划目标为 `off`，对象有效读数仍为 `on` | 「开启 · 设备 · 更新时间」；灯亮，计划只加虚线覆盖层 | 「待确认执行」 |
| 指令已发出，对象仍为有效 `on` | 仍显示开启、灯亮 | 「指令已发出 · 等待设备回读」 |
| 对象有效读数先变为 `off`，执行结果尚未确认 | 「已关闭 · 设备 · 更新时间」；灯灭 | 保留已收到的执行状态，提示「设备已关闭，执行结果待更新」 |
| 执行返回 `confirmed`，未收到配套有效对象更新 | 按现有有效读数显示；若已失效则显示未知，不补 `off` | 「执行结果已确认 · 最新设备读数待同步」，保留结果证据时间 |
| 执行失败，但随后收到有效 `off` | 当前实况仍显示已关闭、灯灭 | 保留「执行失败」与可用错误说明，不把外部变化改写为本次执行成功 |
| 有效对象 `off` 与执行确认均到齐 | 设备显示已关闭；关闭不等于断电，`power_state` 另列 | 「客厅灯 · 已关闭 · 设备回读 · <readback_at>」 |

设备行的时间来自对象 `updated_at`，执行回读时间来自 `readback_at`，人工时间来自 `confirmed_at`。不互相补齐，不用页面加载时间冒充证据时间；演示全程显著标注「模拟数据」。

### 3.1 四类任务行与主按钮

右栏按检查顺序展示四个对象，以小标签明确分组；不把所有行都做成可执行复选框。

| 对象 | 计划 / 检查归属 | 默认上屏内容 | 可用入口 |
| --- | --- | --- | --- |
| 玄关门 `entry_door` | `manual` | 「玄关门 · 待现场确认」 | 点行定位；「现场确认」。无远程关门按钮。 |
| 阳台门 `balcony_door` | 只读核实；计划若提供该行则为 `check` | 「阳台门 · 已合上 · 门磁」+ 证据时间 | 点行定位；「重新读取」。不称为已上锁。 |
| 客厅灯 `living_room_light` | `action` | 「建议关灯」；同时显示当前开启与建议原因 | 复用计划 `selected`，基线为勾选；点击名称查看详情，复选框只改变候选选择。 |
| 卧室空调 `bedroom_ac` | `keep` | 「保持运行 · 猫留在卧室」 | 点行定位；显示保留原因，无执行勾选框。 |

基线 fixture 的 `plan.items` 目前有灯、空调和玄关三行。阳台检查卡来自对象读数，页面不自行创建它的 `item_id` 或执行结果，也不把它计入执行项数。

主操作随阶段变化：

| 阶段 | 右下主按钮 / 反馈 |
| --- | --- |
| 意图、留家约束待确认 | 「查看离家计划」；对应 DS A1 的生成计划动作。只改变文案，不假定已有接口。 |
| 预览计划，已选客厅灯 | 「确认关灯（1 项）」；按钮上方写「仅执行已选动作」。若有多个合法动作则为「确认执行（N 项）」。 |
| 人工确认面板打开 | 同一固定操作区显示「我已确认关闭」，旁列「稍后核实」；提交后返回原计划，恢复关灯主按钮。 |
| 玄关选择稍后核实 | 继续提供独立关灯按钮；上方保留「玄关门仍待核实」，不封锁无关动作。 |
| 执行中 / 待回读 | 主位显示「等待设备回读」并禁止重复提交；保留次级「刷新状态」。 |
| 超时 / 部分失败 | 超时优先「刷新状态」；部分失败先「查看失败项」，刷新并重新确认后才提供「重试失败项」。 |
| 已收到结果 | 主位为「查看逐项结果」；结果已展开时显示「刷新状态」。不提供笼统的一键“安全离家”结论。 |

没有选中可执行项时禁用执行按钮并说明原因。`manual/check/keep` 从不混入执行提交。普通门确认和顶栏「我已出门」不共用提交按钮。

### 3.2 全屋、房间、设备切换时保留的上下文

| 切换 | 改变的界面 | 必须保留的任务上下文 |
| --- | --- | --- |
| 全屋 → 房间 | 相机聚焦房间，面包屑更新；详情区展示该房间对象 | `task_id`、`plan_version`、原始意图、`user_away`、`occupancy`、`retain_room_ids`；完整计划仍可访问。 |
| 房间 → 设备 / 点击提醒 | 选中对应 `object_id`，定位并打开详情；同一对象的提醒、计划行、热点联动 | 各 `item_id` 的分组、勾选、原因和证据；人工记录、待办、各执行结果、回读时间均保留。 |
| 设备 A → 设备 B | 只改变选中与详情；待回读项继续在任务区更新 | 不清除 A 的执行状态，不重新生成计划，不改变 B 的开关或人工记录。 |
| 设备 → 房间 / 返回计划 | 详情收起或回到房间；回到原计划/结果及阅读位置 | 留家条件、勾选、未完成检查、已有结果、能源提示和同一任务阶段。 |
| 任意视角 → 全屋复位 | 复位镜头、清除空间选中，面包屑回全屋 | 不重置设备读数、计划虚线层、勾选、人工记录、执行进度或能源提醒。 |

空间导航与任务步骤独立：全屋复位不是演示复位。未来演示复位由数据提供方恢复基线对象、人工记录、计划与能源提示，本稿不在主线提供该按钮。选择发生在 `baseline_apartment` 内；未来跨模板缓存按共享约定区分 `(template_id, shared_id)`，不在本轮规定切模板实现。

## 4. 约 60 秒离家主线

复用 DS「路径一」，加入独立查看计划与逐项结果的停留。下面是演示讲解节奏，不是后端延迟或超时承诺；不能为凑时长自动合成成功读数。

前提：模拟基线，`user_away=false`；玄关无证据，阳台门磁有效 `closed`，客厅灯有效 `on`，卧室空调有效 `on`。用户声明后为 `occupancy=occupied`、`retain_room_ids=["bedroom"]`。

| 时间 | 用户行为 | 页面反馈与验收点 | 复用 DS |
| --- | --- | --- | --- |
| 0–10 秒 | 输入「我出门两小时，猫留在卧室」，确认留家条件 | 任务上下文显示「猫留卧室 · 保留卧室空调」。顶栏仍为「本人：未出门」。 | A1 |
| 10–18 秒 | 点「查看离家计划」，浏览四项 | 玄关待人工核实，阳台已合上·门磁，客厅灯建议关灯，空调保持运行。灯仍亮，空调继续运行；计划只用虚线表达。 | A2、B1、B4 |
| 18–23 秒 | 点「玄关门 · 待现场确认」 | 未来定位 `entry_door` 的玄关锚点；右侧同步打开该对象详情。本轮文档只描述效果。 | B1 |
| 23–31 秒 | 现场核实后点「我已确认关闭」 | 保存成功后显示「玄关门 · 住户已确认关闭」「人工确认 · <confirmed_at>」。不触发「我已出门」。若保存未确认，仍保留待核实。 | B2 |
| 31–40 秒 | 返回计划，检查客厅灯勾选，点「确认关灯（1 项）」 | 明确只执行客厅灯；执行前复核计划版本、留家条件和相关读数。空调仍因猫留卧室而保留。 | A2、C1 |
| 40–48 秒 | 查看执行中状态 | 「指令已发出 · 等待设备回读」。对象读数仍有效 `on` 时灯保持亮；若读数失效改为未知，而非永久保持“有效开启”。 | C2 |
| 48–56 秒 | 查看收到的有效对象回读及逐项执行结果 | 有效 `off` 更新灯光与设备详情；执行 `confirmed` 单独更新结果行。玄关人工确认、阳台门磁检查、空调保留原因分别展示，不统称为四项执行成功。 | C5 |
| 56–60 秒 | 点「全屋复位」，总览结果 | 回到全屋镜头，任务结果与实况保留。显示「执行：1 项已确认；人工：1 项已核实；门磁：已合上；保留：卧室空调」。本人状态仍独立。 | 路径一第 7 步 |

「我已出门」可在用户实际出门后另行操作，不是上述门确认的副作用，也不作为独立关灯的强制前置条件。猫仍留卧室时，即使本人已出门也仍为 `occupancy=occupied`。

| A2 计划预览 | 展示 `action/keep/manual`；阳台另作只读检查 | 确认选中动作；计划虚线不改变任何实况。 |

| B1 玄关待确认 | 「玄关门 · 待现场确认」「尚未人工核实」；无虚构来源、时间 | 现场确认；定位玄关不产生记录。 |
| B2 玄关已确认 | 「住户已确认关闭 · 人工确认 · <confirmed_at>」 | 回到计划。模型仅在收到对应有效人工对象状态后更新，不能靠点击改姿态或写记录。 |
| B3 玄关稍后核实 | 「玄关门 · 稍后核实」始终留在待办；汇总仍有 1 项待核实 | 保留「继续核实」入口；允许独立关灯。稍后完成时再记录本任务人工确认。 |
| B4 阳台门磁有效关闭 | 「阳台门 · 已合上 · 门磁」及更新时间；不推断上锁 | 重新读取；有效状态驱动门姿态。 |
| B5 门磁离线 / 过期 | 「阳台门 · 状态未知 · 设备离线」或「读数已过期」。有历史证据才加「最后读数：已合上 · <last_known_at>」 | 重新读取；仍无有效读数则保持未知。3D 标未知，旧姿态不作为关闭证据；独立关灯仍可进入复核。 |
| C1 确认前变化 | 「客厅灯状态变化，请重新确认受影响条目」；约束或版本变化也说明影响范围 | 返回受影响条目复核；受影响项在重确认前不提交。保留无关选择和记录，是否重发整单由后端契约确定。 |
| C2 指令发出 / 待回读 | 「指令已发出 · 等待设备回读」；显示目标与实际状态两行 | 禁止重复提交，可刷新状态；3D 只随对象读数更新。 |
| C3 回读超时 | 「结果待核实 · 回读超时 · 请先刷新设备状态，再决定是否重试」；不自动标失败或成功 | 主按钮刷新状态；查询最新读数及执行结果，再判断是否重试。失效读数归未知，历史行须有证据。 |
| C4 部分失败 | 汇总「部分完成 · N 项已确认 / M 项失败」，逐行保留各自结果；其他 pending/unknown 项另列 | 查看失败项 → 刷新 → 必要时确认重试失败项；不重复成功项。每个对象仍按自身读数显示。 |
| C5 回读确认 | 结果行「客厅灯 · 已关闭 · 设备回读 · <readback_at>」，设备实况另列来源、时间 | 查看逐项结果；只有有效对象 `off` 驱动灯灭，执行确认不是动画开关。 |
| D1 日超额 | 「今日用电超出参考线」「今日 12 kWh · 比参考线 10 kWh 多用 2 kWh」 | 查看省电计划；不自动执行。 |
| D2 低备电叠加 | 「备电电量偏低 · 15%（保留线 30%）」用于 DS 的 `low_backup` 示例 | 进入同一省电预览；电池只读，无热点亦不算加载失败。 |

执行状态完整映射：`pending` →「待执行」，`running` →「执行中」，`awaiting_readback` →「等待设备回读」，`confirmed` →「执行结果已确认」，`failed` →「执行失败」，`unknown` →「结果待核实」。只有明确的超时证据才补「回读超时」原因；具体期限与返回时序留给后端，不在页面设定任意秒数。超时不自行改成 `failed`。

失败项复用「执行失败：<error>」，没有错误详情时写「未提供失败详情」。其设备当前可能开启、关闭或未知，不能一律写「保持最后状态」或「未达到目标」。确认失败、超时和对象状态变化都需要可重复走查，不用提示消失代替解决问题。

部分失败需要多条合法 `action`。猫留卧室的基线只有客厅灯一项动作，不能为了演示部分失败把空调加入关机。本分支待后端提供全员离家且用户另行勾选空调等合法多动作样例。

### 5.1 能源备用入口

能源提醒放在右栏计划区下方，折叠为一行提醒和「查看省电计划」，不弹窗打断人工核实。进入预览后保留同一任务上下文与留家约束，计划版本及去重动作由后端提供，本轮不设计自动省电授权流程。

- 日超额复用 12 kWh / 10 kWh / 多用 2 kWh；口径为 `household_consumption`、`Asia/Shanghai` 当地自然日。若为 `grid_import`，改标「购电预算」。同日重复采样合并提醒，不重复添加执行项。
- 指标以 `energy.measurements` 及其来源、时间、可用性、`data_kind` 为准；模拟或估算必须注明，失效值显示未知。旧兼容投影不另建第二套真值。
- 省电预览只建议满足允许动作和当前条件的设备；猫留卧室时空调继续保留。提醒、预测与估算不写成已节能成果。
- 日超额与低备电同时指向客厅灯时，保留两个提醒原因、一个动作入口。低备电仅考虑 `backup_circuit=connected` 的合适负载；电池保持只读。
- 共享约定能源示例为 25% / 保留线 30%，DS `low_backup` 分支为 15% / 30%；页面跟随所选样例，不把二者混成同一快照。本轮只预留提醒和计划入口。

## 6. 3D 预留状态与交互边界

### 6.1 容器的三种预留状态

| 状态 | 左侧显示 | 可用操作与右栏关系 |
| --- | --- | --- |
| 占位 / 尚未接入 | 中性灰底、简化房间示意及「3D 户型待交付接入」。说明模型用于空间定位，当前规格可先查看任务流程 | 禁用相机、热点等依赖模型的控件并说明原因；右侧可审阅状态稿，不将占位图当成实况。 |
| 加载中 | 同尺寸骨架与「正在加载小公寓户型…」。没有真实进度就不显示百分比 | 保留右侧任务与详情；点击提醒可打开文字详情，并提示「户型加载中，暂无法定位」。不自动积累相机跳转队列。 |
| 加载失败 | 「3D 户型暂时无法显示」与「重新加载 3D」，保留图例和文字对象入口 | 只重试模型资源，不复位任务或发送设备动作；右侧状态仍可阅读。未来具备数据链路时，明确对象的文字确认流程可独立使用。 |

## 7. 后续对接顺序与待建模侧确认项

### 7.1 按顺序推进的验收门槛

1. **建模侧确认交付版本后，先验小公寓空间链路。** 确认资产、映射及运行时版本；依次走「全屋复位 → 玄关提醒定位 → 客厅灯点选」。看到四房间全貌、正确玄关锚点，以及同一 `object_id` 的设备详情；导航期间任务上下文不变。
2. **再验计划高亮与实况更新互不干扰。** 在有效灯亮时打开关灯计划，灯继续亮；单独注入有效 `off` 后灯灭、计划和选中仍在；仅更新执行状态不改变灯。再验离线/过期未知、无历史证据不补历史，以及全屋复位不重置数据。这一步用明确标注的本地模拟数据，不代表后端已接通。
3. **最后接后端计划、人工确认、执行与回读。** 验证任务与计划版本、允许动作、独立的本人声明、人工记录保存、执行前复核、重复提交复用已有结果、逐项回读，以及第 5 节异常。基线通过后才扩展大户型与能源分支。

本轮只规定以上顺序，不执行其中的模型集成、状态桥接或后端接线。
